## 0. 结论摘要

| 项 | 结论 |
|---|---|
| FW1 的主问题不是「校验」，而是**装载器缺少「非通用住户」这一层**：`configfile` / `toolhead` 注册的对象名与配置节名不同（`[printer]` → 对象 `toolhead`），且 `[printer]` 没有任何对象叫这个名字 | 建议给 `section!` 增加 `phase`（`early`/`generic`/`late`）与 `object = "<name>"` 两个声明位，或退一步在 `load_config` 里加一小段显式的 early/late 住户注册 |
| 访问追踪需要能在**只读**访问器上记录：追踪值要带上解析后的类型（上游 `settings` 状态直接用返回值），而我们现在的访问器只返回原始字符串，类型解析散在各 extras 的 helper 里 | 建议引入 `ConfigWrapper`（上游同名），把 `get/getint/getfloat/getboolean/getchoice` 与追踪收到一处；`ConfigSection` 保持纯数据 |
| `ConfigSection.parameters` 现在是 `HashMap`，迭代顺序不确定，而 `check_unused` / `raw_config` **依赖节内选项顺序**（上游按文件顺序报第一个错） | 短期至少让校验与状态输出按键排序；最好让参数表保持插入序 |
| FW1 验收里的 `[stepper_x]` 依赖 C1，当前不可达 | 建议把 FW1 验收改成「`[output_pin fan]` 多写一个选项报选项错 + `[printer]` 经住户装载 + `objects/list` 出现 `configfile`」，把 `[stepper_x]` 留给 FW5 |
| FW3 的骨架其实已经有两半：`CommandError`（gcode）与 `ApiError::Internal/CommandError`（API crate）；缺的是**把 `Internal` 收敛、把 handler 异常落到 `invoke_shutdown`、以及 config 错误与 shutdown 的分离** | 建议：新增 `ConfigError`；`KlippyError` 加 `Config(ConfigError)` 变体；`process_line`/`Api::dispatch` 加 `catch_unwind`；主机侧引入 `set_error_state`（用上已经定义却从未赋值的 `PrinterState::Error`） |
| 两个「已经埋好但没接线」的事实 | `PrinterState::Error` 只出现在 `as_category` 与其单测里（`printer.rs:69,850`）；`ApiError::is_internal()` 除了单测没人调用（`protocol.rs:331`）——FW3 正好是接线 |

## 1. FW1 配置装载框架收尾

### 1.1 上游行为（证据）

**装载顺序 / 住户**（`klippy/klippy.py:36-40`、`:114-127`）：

1. `Printer.__init__` 先装 early 对象：`gcode` + `gcode_io`（`gcode.py:492-494`）、`webhooks` + 两个 helper（`webhooks.py:564-567`）。
2. `_read_config()`：
   - `self.objects['configfile'] = PrinterConfig(self)`（`klippy.py:115`）——**对象名与任何节名无关**；
   - `for m in [pins, mcu]: m.add_printer_objects(config)`（`klippy.py:120-121`）——`pins` 注册 `'pins'`（`pins.py:137-138`），`mcu` 注册 `'mcu'` 与每个 `[mcu *]`（`mcu.py:1239-1246`）；
   - `for section_config in config.get_prefix_sections(''): load_object(...)`（`klippy.py:122-123`）——通用遍历，按**文件顺序**；
   - `for m in [toolhead]: m.add_printer_objects(config)`（`klippy.py:124-125`）——`toolhead` 注册 `'toolhead'`，`ToolHead(config)` 读的是 **`[printer]` 节**（`toolhead.py:200-211`、`:604-615`），随后注册 extruder 与 `gcode_move/homing/idle_timeout/...`；
   - `pconfig.check_unused_options(config)`（`klippy.py:127`）。

**结论**：上游的 section→object 有**两种**入口——通用 `load_object`（对象名=节名）与住户显式 `add_object`（对象名自己定，节名另说）。`configfile`/`pins`/`toolhead` 属于后者。

**访问追踪当 schema**（`configfile.py`）：

- `ConfigWrapper._get_wrapper`（`:29-64`）在 `note_valid=True`（默认）时把 `(section.lower(), option.lower()) -> v` 记入共享的 `access_tracking`；取默认值且 `default is not None` 也记；`getlist/getintlist/...` 走同一层，`getchoice` 先取值再校验。
- `ConfigValidate.check_unused`（`:424-445`）：
  - `valid_sections` = 已注册对象名 ∪ `access_tracking` 里出现过的节（**这是 `[printer]` 合法的唯一理由**）；
  - 节不在 `valid_sections` → `Section '%s' is not a valid config section`；
  - 选项不在 `access_tracking` → `Option '%s' is not valid in section '%s'`；
  - autosave 里的选项豁免（`start_access_tracking`，`:416-422`）。
- `_build_status_settings`（`:447-449`）把 `access_tracking` 转成 `settings`，`ConfigValidate.get_status` 返回 `{'settings': ...}`（`:451-452`）。
- `PrinterConfig._build_status_config`（`:544-549`）用 `note_valid=False` 读全部选项构成 `config` 状态；`PrinterConfig.get_status`（`:550-555`）合成 `{config, warnings, save_config_pending, save_config_pending_items, settings}`。
- `PrinterPins` **没有** `get_status`（`pins.py:60`），所以 `objects/list` 里没有它；`configfile` 有，因此**会出现在 `objects/list`**。

**注意**：追踪键做了 `.lower()`，而 `configparser` 默认把选项名小写；本仓库解析器**保留原始大小写**，移植时要显式小写化比较（节名与选项名都要）。

### 1.2 本仓库现状（证据）

- `load.rs:56` `LoadConfig = fn(&ConfigSection, &Arc<Printer>) -> Result<Arc<dyn PrinterObject>, String>`；`load_config`（`load.rs:128-166`）顺序为：`gcode`、`pins`（硬编码）→ 表内主节 → 表内前缀节 → 未认领节检查。没有 late 阶段。
- `load.rs:162` 未认领节直接 `KlippyError::Internal("Section ... is not a valid config section")`；`load.rs:195` 工厂错误 `map_err(KlippyError::Internal)`。文件头注释（`load.rs:32-35`）自己写明「Option-level validation … does not exist yet」。
- 表由 `build.rs` 从 `section!` 生成（`mcu/mod.rs:44`、`extras/output_pin.rs:46` 等）；生成结果见 `target/.../section_factories.rs`。只有「对象名=节名」一种注册方式。
- `ConfigSection`（`config/section.rs:12-30`）是纯数据：`key/id/sub/parameters: HashMap`；访问器 `get/get_str/get_text/get_list/get_list_of_lists`（`:110-176`）**不做任何记录**，且返回原始字符串；布尔/整数解析散在 `extras/bus_debug.rs:43-68`、`extras/output_pin.rs:207-232`。
- `Printer::add_object`（`printer.rs:337-350`）重复名报 `KlippyError::Internal`；`load_config` 的错误在 `klippy.rs:290-292` 被 `invoke_shutdown`（类别 shutdown，不是 error）。
- 没有 `configfile` 对象、没有 `[printer]` 的消费者、没有 `toolhead`。
- 验收目标 `[stepper_x]` 需要 C1（stepper/kinematics），当前不存在。

### 1.3 差距清单

| # | 差距 | 影响 |
|---|---|---|
| F1-1 | 没有 option 级追踪 | 任何真实 printer.cfg 的合法选项若未被读，无法区分「拼错」与「合法但未用」；`configfile.settings` 无法实现 |
| F1-2 | 未认领判定只看 `claimed`，不看「被读过」 | `[printer]` 这种「有节、无同名对象」的节必然报错 |
| F1-3 | 没有住户注册（对象名≠节名 / 无节对象） | `configfile`、`toolhead` 无处安放 |
| F1-4 | 没有 late 阶段（`[printer]` 要在前缀节之后） | toolhead 的默认模块与 extruder 装载顺序无法复刻 |
| F1-5 | `parameters` 是 `HashMap` | 报错选哪个选项、`raw_config` 字段顺序不确定，测试会飘 |
| F1-6 | 访问器只有字符串 | `settings` 的状态值形态与上游不一致；类型解析逻辑重复 |

### 1.4 设计选项与建议

#### (a) 追踪挂在哪：`ConfigSection` 内 vs `ConfigWrapper`

**选项 A：给 `ConfigSection` 加内部可变追踪**（`access: Option<Arc<Mutex<AccessTracking>>>`，`get_*` 里 `note()`）。
优点：`LoadConfig` 签名与所有调用点不动；`register()` 克隆节时 `Arc` 共享，覆盖值也照记。
缺点：把「值类型」变成带副作用的类型；`Debug`/测试构造要处理；`note_valid=False` 只能靠另立方法。

**选项 B（建议）：引入 `ConfigWrapper`**，与上游同名同形：

```rust
pub struct ConfigWrapper<'a> {
    config: &'a Config,
    access: &'a AccessTracking,
    section: &'a ConfigSection,
}
impl ConfigWrapper<'_> {
    pub fn section(&self) -> &ConfigSection;
    pub fn get(&self, option: &str, default: Option<&str>) -> Result<String, ConfigError>;
    pub fn get_float(&self, option: &str, default: Option<f64>, lim: Limits) -> Result<f64, ConfigError>;
    pub fn get_bool(...); pub fn get_int(...); pub fn get_choice(...);
    pub fn get_list(&self, option: &str, sep: char) -> Option<Vec<String>>;
    pub fn getsection(&self, name: &str) -> Option<ConfigWrapper<'_>>;   // 上游 getsection
    pub fn get_untracked(&self, option: &str) -> Option<String>;          // note_valid=False
}
pub type LoadConfig = fn(&ConfigWrapper, &Arc<Printer>) -> Result<Arc<dyn PrinterObject>, ConfigError>;
```

优点：追踪、类型化、默认值、范围检查、`note_valid=False` 全在一处；追踪不会污染 `ConfigSection`；`getsection` 让住户能读别的节（上游常见）。
代价：改 `LoadConfig` 签名 + 6 个 extras/`mcu` 的工厂与 helper + 测试构造；一次性的、可控。

**建议 B**，并把 `bus_debug.rs` / `output_pin.rs` 里手写的 `get_bool`/`parse_int`/`get_float` 收进 wrapper（上游语义一致，错误文案也能对齐）。

#### (b) 追踪值：名字还是（类型化的）值

- 只做 schema 校验只需要键。
- `configfile.settings` 需要值；上游存的是**解析后的返回值**（`getfloat`→float、`get`→str、`getlist`→tuple）。
- 建议 `AccessTracking` 存 `BTreeMap<(String, String), serde_json::Value>`（键都小写），wrapper 的类型化访问器写入对应 JSON 类型；这同时给 `settings` 一个确定形状。
- 若想先小步落地，可先只存 `ConfigValue`（原始文本）并让 `settings` 报字符串——但要在文档里写明与上游 `settings` 的差异。

#### (c) 住户与阶段（本项的核心）

推荐给 `section!` 增加两个可选声明位，`build.rs` 把它们带进生成表：

```rust
section!("printer", order = 10, phase = late, object = "toolhead", load = load_config);
```

- `phase`：`early`（在通用遍历前，如 `mcu`）/ `generic`（默认）/ `late`（在通用遍历后，如 `printer`）。
- `object = "<name>"`：注册名覆盖；缺省仍是节名。这样保留「loader 统一注册、重复名统一检查」的契约（`load.rs` 文档强调的“静态表是唯一入口”不被破坏）。
- 住户的默认模块（`gcode_move`/`homing`/…）仍作为各自 `section!` 条目，用 `phase = late` 或由 toolhead 显式装载——按 C1 的取舍定，FW1 只需**提供**阶段位。

如果不愿动 codegen，退一步：在 `load_config` 里照上游写一小段显式注册（`configfile`、`pins`、late 的 `toolhead`），并加注释说明「这是上游 `_read_config` 的住户，不是通用 extras」。但这与 `load.rs` 的「唯一入口」契约有张力，需要同步改文档。

#### (d) 未认领判定

`check_unused` 的判定应为：

```
valid_sections = claimed ∪ access_tracking.sections
节：identifier.lower() 不在 valid_sections → "Section '<id>' is not a valid config section"
选项：parameters 的每个 key 小写后不在 access_tracking → "Option '<opt>' is not valid in section '<id>'"
```

`[printer]` 靠 `access_tracking` 合法；`configfile` 这类无节对象靠「已注册」合法。

#### (e) 参数顺序

上游 `configparser.options(section)` 是插入序，`check_unused` 报第一个坏选项。建议：

- 最小改动：校验与 `raw_config` 输出前对 `parameters` 的键排序（`BTreeMap` 语义）；
- 更贴上游：把 `parameters` 换成保序结构（`Vec<(String, ConfigValue)>` + 名字索引，或引入 `indexmap` 之类的轻依赖）。仓库目前没有 `indexmap`，加依赖需权衡。

#### (f) `configfile` 对象与范围

FW1 只做：注册 `configfile` 对象、`get_status`（`settings` + `config` + `warnings`）。**autosave / `SAVE_CONFIG` / `deprecate` 建议单列一条**（它们各自有 gcode 命令、文件写入与重启语义，属模块而非框架），在 TODO 里标明依赖 FW1。

## 2. FW3 错误词汇框架

### 2.1 上游行为（证据）

**四类错误**：

| 类 | 上游 | 语义与归宿 |
|---|---|---|
| 用户 G-code 错 | `gcode.CommandError`（`gcode.py:8`），`GCodeCommand.error` / `GCodeDispatch.error`（`:25` `:100`），`Printer.command_error`（`klippy.py:27`） | `_process_commands` 捕获 → `_respond_error`（`!! …`）+ `gcode:command_error` 事件，**不停机**（`gcode.py:222-229`） |
| 配置错 | `configfile.error`（`= configparser.Error`），`Printer.config_error`（`klippy.py:26`），`PrinterPins.error`（`pins.py:8`） | `_connect` 捕获 → `_set_state(msg+message_restart)`，类别 **error**（可 RESTART），**不 shutdown**（`klippy.py:136-139`） |
| MCU/协议错 | `mcu.error`、`msgproto.error` | `_set_state` + `klippy:notify_mcu_error`，类别 error（`klippy.py:140-147`） |
| 其它 = 内部错 | 裸 `except:` | G-code：`invoke_shutdown('Internal error on command:"X"')` + `_respond_error`（`gcode.py:230-234`）；WebRequest：`invoke_shutdown("Internal Error on WebRequest: <method>")` + error 回复（`webhooks.py:271-276`）；connect：`_set_state("Internal error during connect: …")`（`klippy.py:148-153`，**不 shutdown**）；ready 回调：`invoke_shutdown`（`:154-160`） |

**状态类别**：`_set_state` 只写 `state_message`，`in_shutdown_state` 决定 `get_state_message` 报 `error` 还是 `shutdown`（`klippy.py:48-56`）。`invoke_shutdown` 才把 `in_shutdown_state` 置真并 `_set_state`（`:204-210`）。

**其它相关**：`Printer.add_object` 重复名与 `lookup_object` 未命中都报 **config_error**（`klippy.py:71-82`）——不是内部错。

### 2.2 本仓库现状（证据）

- `KlippyError`（`error.rs`）只有 `Connection/Protocol/Request/Parse/Internal`，无 Command/Config。
- `CommandError` 在 `gcode.rs:87-115`；`CommandHandler = Fn(&GcodeCommand) -> Result<(), CommandError>`（`:58`）。`run_script`（`:502-512`）把首个错误 `respond_error` 后返回；`gcode/script` 端点映射成 `ApiError::CommandError`（`api/endpoints/gcode.rs:113-117`）。**用户错误目前已经不会停机**（`gcode.rs` 单测 `:359` 也断言了）。
- `process_line`（`gcode.rs:683-720`）直接 `handler(&gcmd)`，**无 catch_unwind**；handler panic 会沿着调用栈（API runtime 的 endpoint 任务）炸掉。
- API 层已有对偶：`ApiError::Internal` 与 `ApiError::CommandError`，`is_internal()`（`crates/klippy-api/src/protocol.rs:305-333`）**除单测无人调用**；`Api::dispatch`（`registry.rs:384-395`）是唯一入口，也没有 catch_unwind，也没有 shutdown 钩子。
- `PrinterState::Error` 已定义却从未赋值（`printer.rs:69,850`）；`invoke_shutdown`（`:562-582`）是唯一的状态变更；`bring_up`（`:689-737`）对任何 `connect()` 错误都 `invoke_shutdown`（`:716-717`）；`load_config` 错误在 `klippy.rs:290-292` 也 `invoke_shutdown`。
- 借 `KlippyError::Internal` 的地方（`grep`）：`load.rs:162,195`（未认领节/工厂拒绝）、`printer.rs:344`（重复名）、`mcu/object.rs:355,385,405,426,446,488,492,540`（`McuConfig::new`、reset、open、connect 包装等）。其中不少其实是 config/connection 错。

### 2.4 设计选项与建议

#### (a) `ConfigError` 的安放

建议：

- 在 `src/core/klippy/error.rs`（或 `config/error.rs`）定义独立类型：

  ```rust
  #[derive(Debug, Clone, PartialEq, Eq)]
  pub struct ConfigError { message: String }
  // Display 直接输出 message（与上游异常文案一致），Error 实现之
  ```

- `LoadConfig` 返回 `Result<_, ConfigError>`；`Printer::load_config -> Result<(), ConfigError>`；`Printer::add_object -> Result<(), ConfigError>`。
- `KlippyError` 增 `Config(ConfigError)` 变体，供 `connect()` 阶段发现的配置错（`McuConfig::new`、`pins` 保留错等）使用；`notify_mcu_error` 的 `match` 已有 `_` 分支，改动小。
- 不建议把 `CommandError` 塞进 `KlippyError`：它属于 gcode 层，API 层已用 `ApiError::CommandError` 表达同一语义，硬合并会制造两个真源。

#### (b) handler 异常 → `invoke_shutdown`

最小、最贴上游的做法（保持 `CommandHandler -> Result<(), CommandError>` 不变）：

```rust
let outcome = std::panic::catch_unwind(AssertUnwindSafe(|| handler(&gcmd)));
match outcome {
    Ok(r) => r,
    Err(_) => {
        let msg = format!("Internal error on command:\"{}\"", gcmd.command());
        error!("{msg}");                       // 上游 logging.exception
        inner.printer.invoke_shutdown(&msg);
        Err(CommandError::new(msg))            // 与 need_ack=false 的 re-raise 对应
    }
}
```

- `default_handler` 内对已注册命令的二次派发（M117/M118/M23）同样要包，或抽一个 `invoke_handler` helper 统一。
- `gcode:command_error` 的触发留 FW4/G1b，但这里返回的 `Err` 已经是它将来挂接的位置。
- 若希望 handler **显式**报内部错（而非 panic），可把返回类型升为两变体枚举（`HandlerError::{Command,Internal}`）；代价是全量 handler 改签名。建议先按上游用 panic 兜底，把枚举作为后续可选项记在 TODO。

#### (c) API 端点的兜底与 shutdown 钩子

`Api::dispatch` 是唯一入口，建议在 `Api` 上装一个「内部错误钩子」：

```rust
pub type InternalErrorHook = Arc<dyn Fn(&str) + Send + Sync>;
impl Api {
    pub fn set_internal_error_hook(&mut self, hook: InternalErrorHook) { ... }
    pub fn dispatch(...) -> Result<Value, ApiError> {
        let outcome = catch_unwind(AssertUnwindSafe(|| /* endpoint/mux */));
        match outcome {
            Ok(Ok(v)) => Ok(v),
            Ok(Err(e)) => { if e.is_internal() { self.notify_internal(&e.to_string()); } Err(e) }
            Err(_) => {
                let msg = format!("Internal Error on WebRequest: {}", request.method());
                self.notify_internal(&msg);
                Err(ApiError::Internal(msg))
            }
        }
    }
}
```

`api::register`（`src/core/klippy/api/mod.rs:107`）把钩子设为 `printer.invoke_shutdown` 的闭包。这样：

- 兑现 `ApiError::Internal` 的文档承诺（`registry.rs:61-63`）；
- `is_internal()` 有真实调用点；
- API crate 仍不认识 `Printer`，依赖方向不变（钩子是 `Fn(&str)`）。

若不愿改 API crate，退一步：只有 `gcode/script` 与 `gcode/*` 端点自己 `catch_unwind`，覆盖面小、会漏。

#### (d) config 错与 shutdown 分开：接上 `PrinterState::Error`

新增：

```rust
/// 上游 `_set_state`：把打印机置为 error 类别（可 RESTART），不触发 shutdown 事件。
pub fn set_error_state(&self, msg: &str) {
    let mut inner = self.lock();
    if matches!(inner.category, PrinterState::Startup | PrinterState::Ready) {
        inner.message = msg.to_string();
        inner.category = PrinterState::Error;
    }
}
```

- `klippy.rs`：`load_config` 失败 → `set_error_state(format!("{err}"))`（可附 `\n` + RESTART 提示，贴上游 `message_restart`），不再 `invoke_shutdown`。
- `bring_up`：`connect()` 返回 `KlippyError::Config(_)` → `set_error_state`；其余维持现状（MCU/协议错已 `notify_mcu_error` + shutdown，FW7 再对齐上游的 error 类别）。
- `invoke_shutdown` 保持不变（真 shutdown）。

**注意**：`bring_up` 目前 `if self.category() != PrinterState::Startup { return; }`，error 类别会被当成「已 halt」不再 connect——这正是上游 `_set_state` 后 `_connect` 不再继续的语义，一致。

#### (e) `Internal` 收敛对照表（建议）

| 位置 | 现在 | 建议 |
|---|---|---|
| `load.rs:162` 未认领节 | `Internal` | `ConfigError` |
| `load.rs:195` 工厂拒绝 | `Internal` | `ConfigError`（工厂签名改 `ConfigError`） |
| `printer.rs:344` 重复名 | `Internal` | `ConfigError` |
| `mcu/object.rs:355` `McuConfig::new` | `Internal` | `ConfigError` |
| `mcu/object.rs:405` `config.open()` | `Internal` | `Connection`（设备打不开不是 bug） |
| `mcu/object.rs:385/426` reset/open 路径 | `Internal`/`Connection` | 复查：I/O 类 → `Connection`；编程前提 → `Internal` |
| `mcu/object.rs:446` connect 包装 | `Connection` | 保持 |
| `mcu/object.rs:488/492/540` 资源、stats handler | `Internal` | 资源配置错 → `ConfigError`；其余保持 `Internal` |
| `Printer::lookup_object` 未命中 | `Option` | 模块侧需要时加 `lookup_object_or_config_error`（上游 `lookup_object` 报 config_error） |

原则：**用户/配置文件可触发 → Command/Config；环境/链路可触发 → Connection/Protocol；其余才是 Internal。**

### 2.5 建议的实施步骤

1. `ConfigError` 类型；`load.rs`/`printer.rs add_object` 改用它；`KlippyError::Config` 变体；`McuConfig::new` 路径改 `ConfigError`。
2. `Printer::set_error_state` + 主机/`bring_up` 分流（config 错 → error 类别）。
3. `process_line` 的 `catch_unwind` → `invoke_shutdown` + `Err`（`invoke_handler` helper）。
4. API 钩子 + `Api::dispatch` 的 `catch_unwind` + `is_internal()` 触发。
5. 文档：`docs/klippy/developer-manual/architecture.md` 的「错误分层」表补 `ConfigError`/厂商级语义；`error.rs` 头注释写清四类归宿。

### 2.6 建议的验收与测试

- 一条 gcode 参数错（如 `SET_PIN PIN=不存在 VALUE=1`）→ `error` 回复、`gcode/state` 仍 `ready`、无 shutdown（已有类似断言，扩到框架层）。
- handler panic（测试里注册一个 panic 的 handler）→ `invoke_shutdown` 被调用、回复 `Internal error on command:"X"`、`analyze_shutdown`/`shutdown` 事件各一次。
- endpoint panic（测试端点）→ `ApiError::Internal` + 钩子收到 `Internal Error on WebRequest: <method>`。
- 坏配置（`[mcu]` 无接口 / 未认领节 / 坏选项）→ 类别 `error`、`RESTART` 后能重载，事件里**没有** `klippy:shutdown`。
- `add_object` 重复名 → `ConfigError`（不是 `Internal`）。
