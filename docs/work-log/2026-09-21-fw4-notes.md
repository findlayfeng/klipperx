## 1. 逐项对照（做了什么）

### 1.1 参数访问器（上游 `klippy/gcode.py:65-96`）

上游一个 `GCodeCommand.get(name, default, parser, minval, maxval, above, below)` 承担全部，
`get_int` / `get_float` 只是 `parser` 不同的包装。本仓库原来只有字符串访问器 + 分散的
`get_*_default` / `get_float_range`，类型解析重复且没有 `above`/`below`。

改动：

- 新增通用 `get<T: PartialOrd + Display>(...)`，错误文案逐字保留（`missing` / `unable to
  parse` / `must have minimum|maximum of` / `must be above|below`）。
- `get_int` / `get_int_default` / `get_float` / `get_float_default` / `get_float_range`
  改为委托 `get`；新增 `get_int_bounded` / `get_float_bounded`。
- `range_error` 从 `f64` 泛化为 `impl Display`（int 与 float 共用同一段文案）。

**有意的偏离**：上游用 Python `str(value)` 格式化边界，`str(1.0)` 是 `"1.0"`；本仓库
`format!("{}", 1.0f64)` 是 `"1"`。这是既有选择（原测试已按 `"1"` 断言），本轮延续。

### 1.2 `get_command_parameters` / `get_raw_command_parameters`（`:38-51`）

- `parameters()` 重命名为 `get_command_parameters()`（贴上游名；调用点 `i2c_device.rs` 已更新）。
- 新增 `get_raw_command_parameters()`：行首即命令时取其后文本；带行号时跳过 `N<digits>`
  并剥掉尾部 `*<checksum>`。用 `to_ascii_uppercase` 找命令（字节数不变，索引安全），
  比上游 `str.upper()` 在非 ASCII 上更保守——G-code 行本就是 ASCII。

### 1.3 `create_gcode_command`（`:244-245`）

`GCodeDispatch::create_gcode_command(command, commandline, params)`，`need_ack=false`
（合成命令从不 ack）。消费者多为运动 / 探测模块（见摘要表），因此它是 **H9/H10 的前置**，
`gcode_macro` 不用它。

### 1.4 `run_script_from_command`（`:237-238`）

上游用它从 handler 内部跑脚本，避开 `run_script` 的 dispatcher mutex。本主机的脚本在调用
任务上同步跑完（模块头注释已说明），两者行为相同；`run_script_from_command` 是实现，
`run_script` 委托它。这是 `gcode_macro` 的直接前置（FW4 验收之一）。

### 1.5 `gcode:command_error` 与错误分支（`:223-234`）

上游：

```python
try:
    handler(gcmd)
except self.error as e:
    self._respond_error(str(e))
    self.printer.send_event("gcode:command_error")
    if not need_ack:
        raise
except:
    msg = 'Internal error on command:"%s"' % (cmd,)
    self.printer.invoke_shutdown(msg)
    self._respond_error(msg)
    if not need_ack:
        raise
gcmd.ack()
```

改动把一个 `Result` 拆成 `HandlerOutcome::{Ok, CommandError, Internal}`，在 `process_line`
里分别处理：

- `CommandError` → `respond_error` + `send_event(GcodeCommandError)`；`need_ack=false` 时
  再把错误向上传（中止脚本），`need_ack=true` 时 ack 该行并继续；
- `Internal`（panic，已在 `invoke_handler` 里 `invoke_shutdown`）→ `respond_error`，
  **不**发事件。

另一个行为差异随之修掉：扩展命令的 `KEY=VALUE` 重解析原来在 handler 之外（`process_line`
里 `?` 传播），现在移进 handler 路径内部，与上游 `register_command` 的
`lambda params: origfunc(self._get_extended_params(params))` 一致，因此 malformed 参数也
是普通 `CommandError`（会被报告、发事件）。

### 1.6 `ack` / `need_ack`（`:54-63`、`:210`）

`ack()` 现在把 `need_ack` 置 false（`Cell<bool>`，因为 handler 拿 `&GcodeCommand`），
所以一个自己 ack 过的 handler 不会被 `_process_commands` 末尾的 `gcmd.ack()` 二次 ack；
`process_line` 在成功路径与 `need_ack` 吞错路径末尾调用 `gcmd.ack()`。

本主机仍无 `need_ack=true` 的生产者（那是 GCodeIO），所以线上行为不变；补的是协议本身。

### 1.7 事件声明

`gcode:` 三个事件都已在 `event/decl/gcode.rs` 声明，但 `request_restart` 原来没有载荷，
而上游是 `send_event("gcode:request_restart", print_time)`。已改为
`event!("gcode:request_restart", { print_time: f64 })`。

`build.rs` 生成的枚举原来 derive `Eq`；`f64` 不实现 `Eq`，所以去掉（只留 `PartialEq`）。
检查过没有代码把 `KlippyEvent` 当 `Eq`/`Hash` 的 key 用，去掉无影响。

## 3. 拍板点：GCodeIO 补不补

`klippy/gcode.py:390-494` 的 `GCodeIO` 是 FW4 剩下的最大一块，TODO 原文给的是二选一：

- **不补（纯 API 主机）**：输入只走 API 的 `gcode/script`。代价是 `debuginput_exit`、
  `is_fileinput`（`request_restart` / `_handle_shutdown` 退 `error_exit`）、`stats gcodein=`、
  `input_log`、`M112` 乱序检测、伪 tty 全部长期缺失；`need_ack` 也一直没有生产者。
- **补**：做成一个独立对象（如 `extras/gcode_io.rs`），并先把 `Printer::send_event` 改成能
  收集 handler 返回值（上游 `klippy/klippy.py:226-227` 返回 `[cb(*params)]`，
  `_do_debuginput_exit` 用 `all(...)` 轮询）。这会改事件处理器签名
  `Fn(&KlippyEvent)` → `Fn(&KlippyEvent) -> bool`，涉及全树注册点。

本轮按「先做完不依赖它的部分」处理，**没有**动 `send_event` 签名。
