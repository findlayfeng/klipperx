# FW5（toolhead 与运动框架）动工前调查（2026-09-21）

本文为 `TODO.md` 框架队列里 **FW5（运动框架，最重）** / **C1** / **H12** 做的动工前调查：
把上游运动栈的层次与契约、本仓库现状、差距、可选设计与建议步骤逐条摆出来。它是一次性
记录，不是规范；定下来的东西应回写 `TODO.md` 与 `docs/klippy/developer-manual/`。

- 上游基线：`third_party/klipper/`（commit `02e71b9`，与覆盖审计一致）
- 本地基线：FW4 提交后的 `master`
- 规模：`toolhead.py` 614 + `kinematics/*.py` 3292 + `chelper` 运动相关 C 约 3100 行

## 0. 结论摘要

| 项 | 结论 |
|---|---|
| 上游运动栈分五层 | **规划**（toolhead：Move / LookAheadQueue）→ **trapq**（梯形移动队列）→ **itersolve + kin_\***（每 stepper 的位置函数）→ **stepcompress**（位置→`queue_step`）→ **steppersync/serialqueue**（发送）；外面由 **motion_quuing** 调度、**clocksync** 供时基 |
| 最难的一块 | `stepcompress.c`（640 行）：把连续位置压成 `queue_step` 的 `(interval, count, add)`，带 `max_error` 与二次偏差控制；整数/时钟回退边界多 |
| 可以纯算法直译的 | `Move` / `LookAheadQueue`（前瞻，~60 行）/ `trapq` 的数据结构与 append/finalize；逻辑直白，适合先做，也方便和上游对拍 |
| 需要新机制 | `clocksync` 的 print_time ↔ MCU clock **回归**（`cmd/clock.rs` 现只有 `get_clock`）；`motion_queuing` 的 flush 调度 |
| 上游 2025 重构 | 输出调度抽到 `extras/motion_quuing.py`（297 行），`toolhead.py` 只做规划；`mcu.py:1083` 经它 `setup_mcu_movequeue` |
| 与 FW6 的循环依赖 | **G28 需要 endstop/trsync（F8）**，而 F8 又依赖运动层；FW5 的验收应在 `G1` 上先闭合，`G28` 与 FW6 联合验收 |
| 建议拆分 | FW5a 时钟/`Coord` → FW5b 规划（Move/LookAhead/trapq）→ FW5c step 生成（itersolve/stepcompress）→ FW5d 输出调度 + toolhead + stepper 资源 → FW5e kinematics + `G1`/`G28` |
| 需要拍板 | ① chelper 重写的范围（是否 FFI 复用 C）；② `G28` 与 F8 的边界；③ `motion_queuing` 是否照搬分层；④ `Coord` / `calc_position` 的 `None` 形状 |

## 1. 上游运动栈（证据）

### 1.1 层次与数据流

```
G-code (G1/G28…)
  └─ ToolHead                      klippy/toolhead.py (614)
       ├─ Move                     一段移动的梯形参数
       ├─ LookAheadQueue           跨段前瞻，算 junction speed
       └─ trapq_append ─────────►  trapq            chelper/trapq.c (273)
                                    按 print_time 的梯形移动链表
  ┌──────────────────────────────►  itersolve       chelper/itersolve.c + kin_*.c
  │                                 每个 stepper 的 calc_position(move, t)
  │                               ►  stepcompress    chelper/stepcompress.c (640)
  │                                 位置序列 → queue_step(interval,count,add)
  │                               ►  steppersync     chelper/steppersync.c (436)
  │                                 → serialqueue → MCU
  └─ MotionQueuing                 extras/motion_quuing.py (297)
       何时 flush（定时器）、kin_flush_delay、need_flush_time/need_step_gen_time
     ClockSync                     klippy/clocksync.py (231)
       print_time ↔ MCU clock 回归；print_time_to_clock = print_time * mcu_freq
     PrinterStepper / Rail         klippy/stepper.py (475)
       每 stepper 的句柄与 config_stepper；多 stepper 一轴 + homing info
     kinematics/*.py              装载、calc_position、check_move、home
```

### 1.2 各层的关键契约

**`Move`**（`toolhead.py:14-118`）：`start_pos/end_pos`（4 轴）、`axes_d`/`axes_r`/`move_d`、
`accel_t/cruise_t/decel_t`、`start_v/cruise_v/end_v`；junction 用**速度平方**表示
（`max_start_v2`/`max_cruise_v2`/`delta_v2`/`next_junction_v2`，另有
`max_mcr_start_v2`/`mcr_delta_v2` 给 `minimum_cruise_ratio`）。纯挤出移动
（`move_d < 1e-9`）单独成支：`accel=99999999.9`、`is_kinematic_move=False`。
`calc_junction(prev_move)` 是 junction deviation 的几何公式；`set_junction()` 把
accel/cruise/decel 三段定下来。

**`LookAheadQueue`**（`:120-198`）：`add_move` 算 junction 并累计 `junction_flush`
（阈值 `LOOKAHEAD_FLUSH_TIME = 0.150`）；`flush()` 是核心 60 行——**反向**遍历求
junction speed（`junction_info`），再**正向**传播 `cruise_v2`，产出待入 trapq 的 move。
纯算法，可直译并对拍。

**`ToolHead`**（`:200-552`）：持有 `commanded_pos[4]`、`print_time`、
`special_queuing_state`（`"NeedPrime"`/`"Priming"`/`""`）、`max_velocity/max_accel/
minimum_cruise_ratio/square_corner_velocity`。关键方法：

- `_calc_print_time()`（`:260-267`）：`print_time = max(est_print_time + BUFFER_TIME_START,
  calc_step_gen_restart(...))`，并发 `toolhead:sync_print_time`；
- `_process_lookahead()`（`:269-298`）：flush lookahead → `trapq_append` 每段 →
  推进 `next_move_time` → 跑 `timing_callbacks`；
- `_flush_lookahead()`（`:300-308`）：清理并回到 `NeedPrime`；
- `flush_step_generation()` / `get_last_move_time()` / `wait_moves()` / `dwell()`；
- `move()`（`:395`）/`manual_move()`（`:410`）/`set_position()`（`:383`）；
- `_drip_load_trapq`/`drip_move`（`:459-493`）：调试/低速注入；
- `get_status()`（`:503`）报 `position`/`homed_axes`/`print_time` 等。

**`trapq`**（`trapq.h`/`trapq.c`）：`struct move { print_time, move_t, start_v, half_accel,
start_pos, axes_r }`；`trapq_append(tq, print_time, accel_t, cruise_t, decel_t, start_pos,
axes_r, start_v, cruise_v, accel)`；`trapq_finalize_moves(tq, print_time, clear_history_time)`
把处理完的段移进 history 并过期；`move_get_coord(m, t)` 是梯形位置公式的求值。

**`itersolve`**（`itersolve.h`/`itersolve.c` + `kin_*.c`）：`struct stepper_kinematics`
持 `step_dist`、`commanded_pos`、`trapq`、`calc_position_cb`（由 `kin_*.c` 的
`*_stepper_alloc` 填）。`itersolve_generate_steps(sk, sc, flush_time)`（`itersolve.c`）
遍历 trapq，跳过与 stepper 无关的段，对活动段调 `itersolve_gen_steps_range`——用
`step_dist` 迭代求步进时刻。`kin_cartesian.c` 极小（`move_get_coord(m,t).x/y/z`）；
`kin_shaper.c`（294 行，input shaper）是唯一复杂的。

**`stepcompress`**（`stepcompress.h`/`.c`）：`stepcompress_append(sc, sdir, print_time,
step_time)` 累积步进；`commit`/`flush` 产出 `queue_step` 的压缩形式。核心是
`max_error`（由 tmc 等的 `STEPCOMPRESS_FLUSH_TIME`/精度决定）与二次偏差
（`QUADRATIC_DEV`）。**这是最需要小心的移植对象**：整数时钟、方向翻转、
`stepcompress_set_last_position`/`reset`/`find_past_position` 的边界。

**`MotionQueuing`**（`extras/motion_quuing.py`）：`allocate_trapq`、`lookup_trapq_append`、
`allocate_syncemitter`（每 mcu/名字一个 stepcompress）、`setup_mcu_movequeue`（
`mcu.py:1083`）、`register_flush_callback`、`get_kin_flush_delay`、
`check_step_generation_scan_windows`、`_advance_flush_time`/`_flush_handler`（`:142-234`，
定时器决定何时把 step 推到 MCU，维护 `last_flush_time`/`last_step_gen_time`/
`need_flush_time`/`need_step_gen_time`）、`flush_all_steps`、`calc_step_gen_restart`、
`note_mcu_movequeue_activity`、`drip_update_time`。

**`ClockSync`**（`clocksync.py:12-175`）：`print_time_to_clock(pt) = int(pt * mcu_freq)`
（本地乘法，print_time 与 clock 同域）；`_update_regression`（`:68-99`）用 EWMA
（`DECAY`）维护 `time_avg/time_variance/clock_avg/clock_covariance`，并带
prediction-variance 的离群剔除；`_update_best_rtt`（`:101`）维护 `min_half_rtt`；
`estimated_print_time(eventtime)` 把系统时间映射到 print_time；`clock32_to_clock64` 扩位。
`SecondarySync`（`:177`）给多 MCU。

**`stepper.py`**：`MCU_stepper`（`:22-260`）持 step/dir 引脚、`step_dist`、
`_build_config`（发 `config_stepper oid/step_pin/dir_pin/invert_step/step_pulse_ticks`）、
`setup_itersolve(alloc_func, *params)`、`set_trapq`、`get_commanded_position`、
`calc_position_from_coord`、`note_homing_end`、`_check_active`（flush 回调）；
`GenericPrinterRail`/`LookupMultiRail`（`:327-460`）把多个 stepper 聚成一轴并带
homing 信息（`position_endstop`/`position_min`/`position_max`/`homing_speed`/
`homing_retract_dist`/`positive_dir`）。

**`kinematics/*.py`**：`load_kinematics(toolhead, config)` 是唯一入口，由 toolhead
按 `[printer] kinematics` 装载（`toolhead.py:242`）。`CartKinematics`（`cartesian.py`，
129 行）是**最小验收目标**：三轴 `stepper.LookupMultiRail` + `setup_itersolve(
'cartesian_stepper_alloc', axis)`，提供 `get_steppers`/`calc_position`/`update_limits`/
`set_position`/`clear_homing_state`/`home_axis`/`home`/`check_move`/`get_status`。
`kinematics/extruder.py` 的 `PrinterExtruder` 与 `DummyExtruder`（默认 extra axis）是
第 4 轴；`calc_position` 的契约允许逐轴 `None`（`homing.py:245` 会判空并报
"Cannot determine position of toolhead on axis"）。

## 2. 本仓库现状（证据）

已有：

## 4. 设计选项与建议

### (a) chelper 重写的范围（**已定：Rust 分层重写；FFI 作为 `[~]` fallback**）

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 全部一次重写** | trapq + itersolve + stepcompress + steppersync + kin_\* 一次做完 | 一步到位 | 3100 行 C 一次落地，风险集中，验收粒度粗 |
| **B 按最小路径分层（建议）** | 先 `cartesian` 一条链：trapq → itersolve(cartesian) → stepcompress → 输出调度；其余 kinematics/kin_shaper 后置 | 每层可单测、可与上游对拍；先跑通 `G1` | 需要先把接口定稳，避免后置层返工 |
| **C FFI 复用 C** | 通过 bindgen 绑定 `chelper` 编译产物 | 快、行为完全一致 | 与"Rust 重写"的定位矛盾；chelper 还拖着 `serialqueue`/`msgblock`/`pyhelper` 一串；跨语言调试与打包成本 |

**建议与决定：B（Rust 分层重写）**。理由：`trapq`/`LookAheadQueue` 是纯算法，直译风险低；
`itersolve`/`kin_cartesian` 极小；真正有风险的只有 `stepcompress`，把它独立成单独任务最稳。
FFI（C）会让项目定位模糊，且 `serialqueue.c`（1096 行）是另一套主机↔MCU 传输，我们已经有了。

**性能前瞻分析**（为什么性能不是这个决策的因素）：

chelper 之所以是 C，唯一原因是 Python 太慢；C 在这里的作用是“摆脱解释器”，不是算法优势。
热路径的量级：

| 项 | 典型值 |
|---|---|
| 打印步进率 | 8k（100 mm/s × 80 steps/mm）～ 60k（300 mm/s × 200 steps/mm）steps/s |
| 本仓库实测 MCU 上限 | STM32F103 @72 MHz 约 340k steps/s（`klipperx stress`） |
| 每次 flush | ~5–10 ms；60k steps/s 下约 500 步 |
| 每步计算 | 位置求值 + 压缩 ≈ 30–80 ns |
| 每次 flush 总计算 | ≈ 40 µs（预算 5–10 ms） |
| 最坏 500k steps/s | ≈ 40 ms/s ≈ 4% 单核，且是突发 |

Rust ≈ C 的数值性能（同一 LLVM、无 GC、可消边界检查）；上游已把 Python↔C 边界压到“每次
flush 一次”，FFI 的调用开销本来就不在热点；Rust 整链还能省掉 Python 解释器与 greenlet 开销。
所以 FFI 没有性能收益，只有构建/依赖（`serialqueue.c` 与本仓库 tokio + `Mcu` 是两套）与
跨语言调试的代价。

**决定**：先用 Rust 分层重写；把“FFI 复用 C”记为 `[~]` 的 fallback，**待真板出现性能问题
再返工**（用现成的 `klipperx stress` 验证）。

### (b) `Coord` 与 `calc_position` 的 `None`（**已定：按 C**）

上游 `Coord` 是 4 元 tuple（`gcode.py:12-17`），`calc_position` 返回 3 元列表且**允许逐轴
`None`**（`homing.py:245` 判空；delta 的 trilateration 会失败）。可选：

- **A `struct Coord { x, y, z, e: f64 }`**：简单、字段可读；但 `calc_position` 的 `None`
  放不进去，得另用 `[Option<f64>; 3]`。
- **B `struct Coord([f64; 4])` + 索引常量**：贴上游的 tuple 语义，`move`/trapq 的 FFI
  形状一致；`None` 同样另说。
- **C `Coord` 用 `[f64; 4]`，`calc_position` 返回 `[Option<f64>; 3]`（建议）**：位置是
  数值，`None` 只出现在"从 stepper 位置反推轴位置"这一处，让它显式出现最清楚。

建议 C，并在 `Coord` 上加 `x()/y()/z()/e()` 访问器保持可读性。

### (c) `Kinematics` trait 的边界（**已定：窄 context**）

按上游 `CartKinematics` 的调用面，trait 至少要有：

```rust
trait Kinematics {
    fn get_steppers(&self) -> Vec<Arc<McuStepper>>;
    fn calc_position(&self, stepper_positions: &HashMap<String, f64>) -> [Option<f64>; 3];
    fn check_move(&self, move_ctx: &mut MoveContext) -> Result<(), CommandError>;
    fn set_position(&self, newpos: Coord, homing_axes: &[char]);
    fn update_limits(&self, axis: usize, range: (f64, f64));
    fn clear_homing_state(&self, clear_axes: &[char]);
    fn home(&self, homing_state: &mut HomingState);
    fn get_status(&self, eventtime: f64) -> Value;
}
```

两个设计点：

1. **`check_move` 的入参**：上游传的是 `Move`（`check_move(move)`）并允许
   `move.limit_speed(...)`（就地改速度/加速度）。Rust 里 `Move` 是 toolhead 的，trait
   若直接吃 `&mut Move` 会把规划类型暴露给 kinematics；可以定一个窄接口
   （`MoveContext { axes_d, move_d, end_pos, limit_speed(..) }`）。
2. **homing 的协议**（C1 已列）：`home_rails(rails, forcepos, movepos)`、
   `set_homed_position(pos)`、`get_trigger_position`、`set_stepper_adjustment`。这些与
   FW6 的 `HomingState` 一起定。

建议：`Kinematics` trait 只定义**toolhead 需要的方法**，`check_move` 走窄 context，
homing 的具体接口与 FW6 联合定（见 (f)）。

### (d) `motion_quuing` 是否照搬分层（**已定：照搬分层，flush 算法逐步对齐**）

- **照搬（建议）**：一个 `MotionQueuing` 对象持有 trapq 列表、每 MCU 的 step 输出、
  flush 定时器与常量；`ToolHead` 只做规划。好处是与上游逐行可对，`STEPCOMPRESS_FLUSH_TIME`
  等常量都在一处；`stepper.rs` 的 flush 回调、`toolhead._handle_step_flush` 都靠它。
- **先简化**：固定频率 flush（例如 5–10 ms）先跑通 `G1`，之后再对齐上游的自适应
  `_flush_handler`（`BGFLUSH_*` 常量与 `kin_flush_delay`）。

建议：**结构照搬、算法先简化**——接口（`note_mcu_movequeue_activity`/`flush_all_steps`/
`calc_step_gen_restart`/`get_kin_flush_delay`）一次定好，先实现"够用"的 flush，再对齐
上游的自适应调度。

### (e) stepcompress 的策略（**已定：独立任务，先简化让流程过**）

- 直译 `stepcompress.c`（640 行）：保持 `(interval, count, add)` 与 `max_error` 语义，
  用整数时钟；风险集中在溢出/方向翻转/`reset`。
- 简化版：不做压缩，直接为每个 step 发一条 `queue_step`（`interval=..., count=1, add=0`）。
  **能跑通但会打爆命令队列**（`move_count` 有限，`queue_step` 数量爆炸），只适合
  极早期冒烟。

**决定**：把 `stepcompress` 的**完整压缩**独立成单独任务（后置，见 FW5f）；FW5 里先写
**简化实现**（每步一条 `queue_step`，`count=1`）让 `G1` 流程能过。简化实现被使用时
**打印告警（最多三次）**，避免每次 flush 刷屏；并在代码注释与 TODO 里各记一处。完整压缩
才是真正需要与上游对拍的部分（(interval,count,add)、`max_error`、`reset`/方向翻转边界）。

### (f) 与 FW6/F8 的边界（**已定：FW5 先到 `G1`**）

G28 需要 `MCU_endstop` + `MCU_trsync`（F8），而 F8 的 `MCU_bus_digital_out`/命令队列
又依赖运动层（FW6 的依赖列写着"只能等 FW5"）。可选：

- **A（建议）** FW5 的验收先只到 `G1`（真板单轴/三轴动），`G28` 与 FW6 联合验收：
  FW5e 提供 `HomingState` 接口与 `none`/固定位置回零，F8 落地后接真实 endstop。
- **B** 把 F8 的 endstop/trsync 最小子集并入 FW5（因为它们与 trapq 的"停止/触发"耦合），
  FW6 只剩 `bus_digital_out`。
- **C** FW5 先做纯 host 层 + 假 MCU 验收，真机 `G1`/`G28` 全留给 FW5+FW6 的合并阶段。

建议 A：把"验收"拆成 host 单测 → 假 MCU → 真板 `G1` → 真板 `G28`（带 F8）四级，
避免为了 G28 把 FW5 和 FW6 绑成一个不可拆的大块。

### (g) 多 MCU 与 SecondarySync / input shaper

`SecondarySync`（`clocksync.py:177`）、`kin_shaper.c`（input shaper，H6）、
`idex_modes`/delta/corexy 等全部**后置**；FW5 只做单 MCU + cartesian。在 TODO 里标清。
