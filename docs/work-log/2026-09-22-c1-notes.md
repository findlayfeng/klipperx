## 0. 结论摘要

| 项 | 结论 |
|---|---|
| C1 的核心 | **轴与 stepper 的抽象**：stepper 不再自带「我是哪个轴」，而是由拥有者（rail / 运动学 / extruder）决定它的位置函数；toolhead 不再写死 `[stepper_x/y/z]` |
| 最难的一块 | `PrinterExtruder` 需要**自己的 trapq**，而 trapq 现在被 `ToolHead` 独占在 `MotionQueuing` 里；这决定了 `MotionQueuing` 的归属 |
| 最大的边界 | `[extruder]` **段**依赖 H1（`heaters::setup_heater`），C1 只能给到**运动部分**；做 C1a 不等于 T3 转绿 |
| 多轴怎么读 | `[stepper_z1]` 没有自己的工厂，按上游是**被 `[stepper_z]` 的拥有者读掉**；本仓库的 loader 需要能读「兄弟 section」（`Printer::config()` 或等价物） |
| 建议拆分 | **C1a 轴/stepper 抽象 + 多轴**（前置，无 heater 依赖）→ C1b extruder 运动（与 H1 配对）→ C1c 运动学族（corexy 先）→ C1d `gcode_move` + print-time 回调 |
| 需要拍板 | ① 多 stepper section 的读法；② `PrinterStepper` 的 solver 参数化；③ `Rail` 归属；④ `MotionQueuing` 归属与多 trapq；⑤ `extra_axes` 接口与 junction 接线；⑥ C1a 的验收边界 |

## 2. 证据：上游的轴与 stepper 模型

### 2.1 `PrinterStepper` 不自带轴，`MCU_stepper.setup_itersolve` 由拥有者调用

`klippy/stepper.py`：

- `PrinterStepper(config)`（`:266`）只读引脚与 `step_dist`，建 `MCU_stepper`；
- `MCU_stepper.setup_itersolve(alloc_func, *params)`（`:74`）由**拥有者**调用，装的是
  `kin_cartesian` / `extruder_stepper_alloc` / 未来 `kin_delta` 的 `calc_position`；
- `MCU_stepper.set_trapq(tq)`（`:230`）：**每个 stepper 各自指向一个 trapq**。

### 2.2 一轴可以有多个 stepper：`GenericPrinterRail` / `LookupMultiRail`

`GenericPrinterRail`（`:326`）：一轴 = N 个 stepper + endstop 集合 + range/homing info。
`LookupMultiRail(config)`（`:455`）以 `[stepper_z]` 为基名，循环读 `stepper_z1`、
`stepper_z2`…（`config.has_section(name+str(i))`，i 从 1 到 98）并 `add_stepper_from_config`。

**关键**：`[stepper_z1]` **没有自己的模块工厂**。上游 `_read_config` 对每个 section 调
`load_object(config, name, None)`（`klippy/klippy.py:123`），第三个参数 `default=None`
使找不到模块的 section **静默跳过**；它的 option 之所以通过 `check_unused_options`，是因为
`LookupRail` 里的 `config.getsection('stepper_z1')` 读过了它们（option 读取即 schema）。

### 2.3 第 4 轴：`ToolHead.extra_axes`

- `ToolHead.__init__`（`toolhead.py:236-241`）：`extra_axes = [DummyExtruder]`，索引 3 起是 E；
- `move()`（`:395`）：`for e_index, ea in enumerate(self.extra_axes): ea.check_move(move, e_index+3)`；
- `LookAheadQueue.add_move` → `Move.calc_junction`（`:64`）：
  `ea_v2 = [ea.calc_junction(prev_move, self, e_index+3) …]` 参与 junction 上限；
- `_process_lookahead`（`:269`）：`ea.process_move(next_move_time, move, e_index+3)`，
  每段调用一次；
- `PrinterExtruder.process_move`（`kinematics/extruder.py:222`）把 E **写进自己的 trapq**
  （trapq 的 x 是挤出量、y 是 pressure advance 标志）；
- `ExtruderStepper`（`:7`）是 `PrinterStepper` + `extruder_stepper_alloc` + 自己的 PA 状态。

### 2.4 `MotionQueuing` 持有多个 trapq

`extras/motion_queuing.py`：`allocate_trapq()`（`:63`）可被任意对象调用并把 trapq 登记进
`self.trapqs`；`lookup_trapq_append()` 交出 append 函数；`steppersync` 按 (mcu, syncemitter)
管理输出。`ToolHead` 与每个 `PrinterExtruder` 各有一个 trapq，stepper 通过 `set_trapq` 绑定。

### 2.5 上游的装载顺序（本仓库需要对应）

`_read_config`：`pins`/`mcu` 先 → 通用 prefix 段（文件顺序，`[extruder]` 在这里，
`load_object('motion_queuing')` 于此时**按需**创建）→ `toolhead`（`[printer]`）后。
本仓库没有「按需 load_object」，只有静态工厂表，这是 §4(d) 要拍板的地方。

## 4. 设计选项与建议（拍板点）

### (a) 多 stepper section（`[stepper_z1]`）怎么读

| 选项 | 做法 | 评价 |
|---|---|---|
| **A 给每个编号段一个工厂** | 生成 `stepper_z1`…`stepper_z98` 的工厂表 | 表爆炸；与上游语义不符 |
| **B loader 支持「家族」** | `section!(family = "stepper_z")`，把 `stepper_z1`… 交给同一工厂 | 新机制，但精确表达「谁拥有这些段」 |
| **C 工厂能读兄弟 section（建议）** | `Printer` 在 load 期间暴露 `Config`，工厂用 `printer.section_wrapper("stepper_z1")` 读；option 读取即认领 | 最小、与上游 `config.getsection` 同形；`check_unused` 已有 `access.sections()` 机制 |

**建议 C**：`Printer::load_config` 期间保存 `Arc<Config>`，提供
`Printer::config()` 或 `Printer::section(id, sub)`，返回挂在同一 `AccessTracking` 上的
`ConfigWrapper`。这样 `[stepper_z]` 的拥有者（见 (c)）能读 `stepper_z1…`，`check_unused`
不会误报。`[extruder1]`、`[manual_stepper]` 同理。

### (b) `PrinterStepper` 的 solver 参数化

上游把 solver 的安装交给拥有者。建议：

- `PrinterStepper` 去掉 `axis: Axis` 字段（或只留作 rail 元数据），加一个
  `solver: Mutex<Option<SolverSpec>>`；
- `SolverSpec { position: PositionFn, active_flags: AxisFlags }`（`PositionFn` 是 `fn`）；
- 新增 `PrinterStepper::setup_itersolve(position, active_flags)`，由持有者在**load** 期调用；
- `connect` 用 `SolverSpec` 建 `Stepper`（无 spec 时按 `axis` 兜底或报错）。

`extruder_stepper_alloc` 的对应物是「读 trapq 的 x」的 `PositionFn` +
`AxisFlags::X`（E 轴复用 `AF_X`，因为 extruder trapq 的 x 就是挤出量）。

### (c) `Rail` 归属：kinematics 还是 stepper section

上游在 kinematics（`LookupMultiRail`）里建 rail。对本仓库：

| 选项 | 做法 | 取舍 |
|---|---|---|
| **A kinematics 建 rail（建议）** | `CartesianKinematics` / `DeltaKinematics` 各自读 `[stepper_x]` + `[stepper_x1]…` 建 `Rail` | 与上游一致；rail 的「怎么用」是运动学的事 |
| B `[stepper_*]` 工厂建 rail | `[stepper_z]` 工厂读 `stepper_z1…` 建 `Rail` 对象，kinematics 按轴查 | 工厂更早（generic），但 rail 概念渗进 stepper 层 |

建议 A：`Rail` 是 `motion` 层的类型（持 `Vec<Arc<PrinterStepper>>` + `HomingInfo` + range），
由 kinematics 在 `[printer]`（late）装载时通过 `LookupMultiRail` 等价物构建。这要求 (a) 的
兄弟 section 读取，且 late 期能构造并注册 `PrinterStepper`（load 期注册，`bring_up` 前完成，
可行）。

### (d) `MotionQueuing` 的归属与多 trapq

extruder 需要自己的 trapq，而 trapq 现在归 `ToolHead` 独占。三个选项：

| 选项 | 做法 | 取舍 |
|---|---|---|
| **A 提前建 host 对象（建议）** | `MotionQueuing` 在 `load_config` 开头作为 host 对象注册（同 `gcode`/`pins`），extruder 与 toolhead 都 lookup 它 | 与上游「`motion_queuing` 是全局对象」一致；改动集中 |
| B `Arc<Mutex<MotionQueuing>>` 共享 | toolhead 持有，extruder 持一份 Arc | 锁进热路径；所有权仍乱 |
| C trapq 独立（`Arc<Mutex<Trapq>>`），`MotionQueuing` 只记列表 | stepper 存自己的 trapq | 改动最大，但不是不行 |

建议 **A**：`MotionQueuing` 提为 host 对象，`allocate_trapq() -> TrapqId`（内部 `Vec<Trapq>`），
`Stepper` 存 `Option<TrapqId>`，`generate` 用自己的 trapq；`finalize_moves` 遍历全部 trapq。
`ToolHead` 持 `ToolHead` 自己的 trapq id，`PrinterExtruder` 持自己的。

### (e) `extra_axes` 接口与 junction 接线

上游 `Move.calc_junction` 直接引 `toolhead.extra_axes`；本仓库 `Move` 是独立类型、
`LookAheadQueue` 在 `ToolHead` 内。建议：

- 定义 `trait ExtraAxis`（`motion` 层）：`name` / `check_move(&mut MoveContext, ea_index)` /
  `calc_junction(prev: &Move, cur: &Move, ea_index) -> f64` / `process_move(&mut MotionQueuing, print_time, &Move, ea_index)` / `get_status`；
- `ToolHead` 持 `extra_axes: Vec<Arc<dyn ExtraAxis>>` 与对应的 `commanded_pos` 第 4 轴；
- `LookAheadQueue::add_move` 接 `&[Arc<dyn ExtraAxis>]`（或 `ToolHead` 在 `add_move` 前把
  extra 的 junction 上限写进 `Move`），避免 `Move` 反向持有 toolhead；
- `process_lookahead` 按上游顺序：主 trapq → 每个 extra 的 `process_move` → timing callbacks。

注意：当前 `Move` 的 `delta_v2`/`min_move_t` 等是 `f64`，junction 用平方速度（与上游一致），
extra 的下限以 `v2` 返回即可。

### (f) extruder 与 H1 的边界（**重要**）

上游 `PrinterExtruder.__init__` 第一步就是 `pheaters.setup_heater(config, gcode_id)`。本仓库
`heaters` 只有**传感器注册表**，没有 `setup_heater`/控制环。因此：

- **C1b（extruder 运动）**：`[extruder]` 的 stepper/trapq/extra-axis/`check_move`/PA 状态；
- **H1（加热）**：`setup_heater` + PID/bang-bang + `M104`/`M109`/`M140`；
- **T3 转绿 = C1b + H1 都落地**（还要 `[fan]`）。分析里不要承诺 C1 单独把 T3 修好。

建议 C1b 把 heater 做成一个可注入的接口（`ExtruderHeater`），C1b 先用「无加热器」的桩，
H1 落地后接上；上游 `check_move` 的 `can_extrude` 判定挂在 heater 上。

### (g) 运动学族的顺序

| 族 | 运行数（首失败） | 做法 | 建议顺序 |
|---|---|---|---|
| corexy / hybrid_corexy / corexz / hybrid_corexz | 11 / 2 / 1 / 1 | `CartesianKinematics` + 2×2 矩阵（`calc_position` 与 `check_move` 用矩阵） | **C1c-1** |
| delta / rotary_delta / deltesian / winch | 13 / 2 / 1 / 1 | 迭代求解 + `mathutil::trilateration`/`gaussian_solve` | C1c-2 |
| generic_cartesian | 4 | 数据驱动的轴定义 | C1c-3 |
| polar | 1 | `mathutil` 的 atan2 映射 | C1c-4 |

corexy 先做：它把 `CartesianKinematics` 抽出「轴变换」这一层，delta 的迭代求解是独立工作。

### (h) `gcode_move` 与 print-time 回调

- `gcode_move`（G4 的落地体）需要 toolhead + `Coord`，已在；建议独立成 **C1d**，因为
  `commands.test` / `out_of_bounds.test` 依赖它（G92/M114/G90/G91/`SET_GCODE_OFFSET`）。
- `toolhead.register_lookahead_callback`（上游 `:417`）是 `SET_PIN` 时序、`pwm_tool`、
  extruder PA 的共同前置；建议同 C1d，作为 `Move.timing_callbacks` 的公开入口
  （`Move` 已有 `timing_callbacks`，只差 `ToolHead` 上的注册方法）。
- `motion_report`（`dump_trapq`/`dump_stepper` 端点）随 H10，不在 C1。

| 2 | `PrinterStepper` solver | **参数化**：`setup_itersolve(position_fn, active_flags)`，`connect` 按 spec 建 `Stepper` |
| 3 | `Rail` 归属 | **A**：kinematics 在 `[printer]` 装载时建 `Rail`（多 stepper 一轴） |
| 4 | `MotionQueuing` 归属 | **A**：提为 host 对象（load 期注册），`allocate_trapq` + per-stepper trapq |
| 5 | `extra_axes` 接口 | `motion` 层的 `trait ExtraAxis`；`LookAheadQueue::add_move` 接 extra 列表，`Move` 不反向持有 toolhead |
| 6 | C1a 验收边界 | 轴/stepper 抽象 + 多轴（`stepper_z1`）；**extruder 段本身留给 C1b+H1** |

> 先做 **C1a**。它不依赖 H1、不改运动数值，能把 T10 的 section 打开，并为 C1b/C1c/T6/S1
> 提供落点。

## 9. C1a 落地说明（2026-09-22）

按上面的拍板做了 C1a，与计划的差异有两处，记在这里（回写进实现的注释）：

1. **`Rail` 住在 `extras/stepper.rs`，不在 `motion` 层。** 拍板说「kinematics 建 Rail」
   指的是**在 `[printer]`（late）装载时建**，这一点做到了——`ToolHeadObject::new` 建三个
   `Rail`。但 `Rail` 持的是 `Arc<PrinterStepper>`，而 `PrinterStepper` 是 extras 类型；
   若把 `Rail` 放进 `motion/kinematics.rs`，运动层就反向依赖 extras。所以 `Rail` 与
   `PrinterStepper` 同层，kinematics（motion）仍只收「轴名 + 范围」。
2. **solver 由 `ToolHeadObject` 装，不是 kinematics 自身。** 原因同上：`setup_itersolve`
   是 `PrinterStepper`（extras）的方法。`ToolHeadObject` 按轴装 cartesian 位置函数；
   C1c 的运动学族在这里分派（corexy 的矩阵、delta 的求解），或改为 kinematics 交出
   solver 描述、由 toolhead 安装。

已做：

- `ConfigWrapper::with_config` / `sibling` / `has_sibling`：loader 把 `&Config` 传给每个工厂，
  兄弟 section 的 option 记录到同一 tracker（`check_unused` 因此接受无工厂的 `[stepper_z1]`）。
- `PrinterStepper::setup_itersolve(position_fn, active_flags)` + `SolverSpec`；`connect` 按
  spec 建 `Stepper`，缺省回退到名字对应的 cartesian 轴。
- `Rail::lookup`：主段 + `…1`/`…2`（同轴）直到缺失；主段提供 range/homing，编号段只读电机
  选项（`position_*`/`homing_*` 只在主段读，`endstop_pin` 两处都读）。
- `ToolHeadObject` 用 `Vec<Arc<Rail>>` 替掉写死的三轴，装 solver、按 rail 注册 endstop、
  取主段的 range 建 `CartesianKinematics`。

验收：`test_a_stepper_z1_joins_the_z_rail`（Z rail 两个 stepper）；回归里
`Section 'stepper_z1'…` 消失，首次失败前移到 `z_tilt`/`quad_gantry_level`（H9）。

### C1c-1 corexy 族（2026-09-22）

按 §4(g) 做了第一族（`corexy`/`corexz`/`hybrid_corexy`/`hybrid_corexz`）。与计划的差异：

- 四个族共用一个 `CartesianKinematics`，差异抽成 `CartesianTransform`（rail 位置 → 台面轴
  的映射）：Standard / CoreXy / CoreXz / HybridCoreXy / HybridCoreXz。`check_move`、homing、
  limits 不分族。
- `itersolve` 加 `corexy_position_fn(plus)` / `corexz_position_fn(plus)` 与对应的 active
  flags（`X|Y` / `X|Z`），对应 `kin_corexy.c` / `kin_corexz.c`。
- `ToolHeadObject` 的 `KinematicsKind` 负责三件事：选每根 rail 的 solver、给出 transform、
  给出 endstop 互挂方向（corexy 双向、corexz 双向、hybrid_* 单向，逐条对 `corexy.py:14-17`、
  `hybrid_corexy.py:17-18`）。endstop 互挂让一根 rail 的触发能停住另一根 rail 的电机。
- 与上游的一个小偏差：hybrid 的 X 段上游用 `LookupRail`（单 stepper），这里统一用 `Rail::lookup`
  （会读 `stepper_x1`）。实际配置不会写这个兄弟段，行为一致。

验收：`itersolve` / `CartesianKinematics::calc_position` 的逐族单测；
`test_the_corexy_family_loads_and_builds_its_rails`。回归里 corexy/corexz/hybrid_* 的首次
失败由 kinematics 前移到 `extruder`（T3）/`dual_carriage`（T9）。

### C1b extruder 运动（2026-09-22）

按 §4(d)(e)(f) 做了 extruder 的运动半边，分三个提交：

1. **运动层**（`f9e16b5`）：`MotionQueuing` 多 trapq + `Stepper::set_trapq`；`ExtraAxis` trait；
   `ToolHead.extra_axes` + `process_lookahead`/`add_move` 接线；`extruder_position_fn`。
2. **heater 桩**（`903f4c3`）：`heaters::setup_heater` + `Heater`（读并认领选项、建 sensor、
   `can_extrude` 固定 true）；控制环（PID/bang-bang/PWM）留 H1。
3. **`[extruder]` 段**：`extras/extruder.rs`。

与拍板（§8 决定 4）的差异：**`MotionQueuing` 没有提为 host 对象**。当时选 A 是为了让
`[extruder]` 在 load 期就能 `allocate_trapq`；实际实现改成「toolhead 在 connect 时把每个
extruder 挂成 extra axis 并分配 trapq」，因为 `[extruder]` 是 generic 段（早于 `[printer]`），
它的 stepper 在 generic connect 就绪，而 toolhead 在 late connect 才拥有 `MotionQueuing`。
这避开了把 `Arc<Mutex<MotionQueuing>>` 塞进热路径，也避开了 host 对象表的新条目。

其余细节：

- `[extruder1]`… 经 `ConfigWrapper::sibling` 读，与 `[stepper_z1]` 同一机制（§4(a)）。
- extruder 的 `PrinterStepper` 以隐藏名 `extruder_stepper <name>` 注册为 printer object，
  这样它的 `connect` 会跑、建出 host `Stepper`，toolhead 再 `take_stepper`。
- extruder 的 trapq 的 x = 挤出量、y = pressure advance 标志（与上游 `trapq_append` 一致）。
- `SET_PRESSURE_ADVANCE` 只记录值；作用在 solver 上的平滑滤波是 H6。
- `can_extrude` 固定 `true`：本机没有上游的 file-output 旁路，而控制环又是 H1；否则所有
  挤出移动都会被冷喷头判据挡住。

验收：`an_extruder_move_runs_against_the_fake_firmware`（`SET_KINEMATIC_POSITION` →
`G1 X10 Y10` → `G1 E1` → `M400`）真的跑过运动轴与挤出机的 `queue_step`；
`check_move`/`calc_junction`/`[extruder1]` 各有单测。回归里 `Section 'extruder'` 消失，
首次失败前移到 `heater_bed`（H1）/`extruder_stepper`（H10）。
