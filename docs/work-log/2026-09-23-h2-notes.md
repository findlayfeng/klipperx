## 0. 结论摘要

| 项 | 结论 |
|---|---|
| H2 的核心 | **`fan.py` 一个文件**：`[fan]` + `Fan` 核心（max_power / kick_start / off_below / enable_pin）+ `M106`/`M107`。静态缺口里 `fan` 被 **197 次运行**引用，其中 **52 次运行「只差 fan」** |
| 最难的一块 | `Fan` 用的 `GCodeRequestQueue`（上游 `output_pin.py` 的排队器）依赖 `toolhead.register_lookahead_callback` + `motion_queuing.register_flush_callback`，两者都是 **C1d**；`heater_fan`/`controller_fan` 另需 `heaters.lookup_heater`（H1 面） |
| 最大的边界 | 回归的量是**静态 section 缺口**，所以 H2-1 先做到「配置能加载」就值 52 次运行转 0 缺口；真正的排队调度（print-time 生效）需要移植 `GCodeRequestQueue`——C1d 已收官，print-time 层已就位，缺的就是这个队列，与 `output_pin` 的余项同源 |
| 与 H1 的交界 | `heater_fan`/`controller_fan` 要按名字查 heater 并读温度 → 需要给 `PrinterHeaters` 补 heater 注册表（`add_heater`/`lookup_heater`/`get_temp`），这是 H1 的 `heaters.py` 剩余部分 |
| 与 F7/F9 的交界 | `tachometer_pin` 需要 `pulse_counter`（F7 未动工）；`led`/`neopixel`/`dotstar` 需要固件 `neopixel.c`（F9）；`pwm_tool` 需要固件 `queued_pwm`（F9） |
| 建议拆分 | **H2-1 `fan`** → H2-2 `fan_generic` → H2-3 `heater_fan`（+heater 注册表）→ H2-4 `controller_fan` → H2-5 pin 芯片类（`multi_pin`/`duplicate_pin_override`/`pwm_cycle_time`/`static_pwm_clock`）→ H2-6 `servo`+`pwm_tool` → H2-7 LED/驱动家族 |
| 需要拍板 | ① kick_start_time 的落地方式；② `tachometer_pin` 报错还是 rpm=None；③ 排队调度先走 immediate；④ H2-3 顺手给 heaters 加注册表 |

### 2.1 `Fan` 核心的四个行为（`fan.py:14-73`）

1. **配置**：`max_power(0<..≤1)`、`kick_start_time(≥0, 默认0.1)`、`off_below(0..=1)`、
   `cycle_time(>0, 默认0.010)`、`hardware_pwm`、`shutdown_speed(0..=1)`、可选 `enable_pin`、
   可选 `tachometer_pin`/`tachometer_ppr`/`tachometer_poll_interval`。
2. **`_apply_speed`**：`off_below` 裁零 → `max_power` 裁顶 → 与上次相同就 discard →
   `enable_pin` 只在 0↔非0 翻转 → **kick start**（从 0 起跳或提速超过 0.5 时，先满速
   `kick_start_time` 再落回目标值，返回 `repeat`）→ `set_pwm`。
3. **`gcode:request_restart`** → 立刻停转（shutdown_speed 是停机值，由 `setup_start_value`
   的第二参交给固件）。
4. **`get_status`**：`{speed: 最后请求值, rpm: 转速}`，`rpm` 只有配了 tachometer 才有值。

`M106`：`S` 缺省 255，`minval=0`、**无 maxval**，除以 255；`M107` = `S0`。

## 3. 差距：本仓库缺什么

### 3.1 排队器（决定 fan/servo 的调度形态）

上游 `output_pin.GCodeRequestQueue`（`output_pin.py:15-73`）要做三件事：按 print_time 排队、
`motion_queuing` 的 flush 回调里逐条消化、`toolhead.register_lookahead_callback` 把 g-code
请求钉到前瞻时刻。本仓库这三样：

| 依赖 | 状态 |
|---|---|
| `mcu.min_schedule_time()` | **没有**（`Mcu` 有 `estimated_print_time`，无 min_schedule_time/max_nominal_duration） |
| `toolhead.register_lookahead_callback` | **没有**（C1d 条目） |
| `motion_queuing.register_flush_callback` / `note_mcu_movequeue_activity` | **没有**（`MotionQueuing` 只有多 trapq，C1b 加的） |

`output_pin.rs` 已经把这件事写成「Scheduling 是 C1」的**先例**：`SET_PIN` 走
`update_digital_out`/`update_pwm` 立即路径。H2-1 沿用同一形态，理由是：回归量是**静态
section 缺口**，immediate 不损失配置可加载性；C1d 落地后单独一个提交把 `GCodeRequestQueue`
补上，`fan`/`output_pin`/`servo` 一起切换（而不是每个 extra 各自发明队列）。

### 3.2 heater 注册表（`heater_fan`/`controller_fan` 的前置）

上游 `heaters.py` 有 `lookup_heater(name)` / `get_temp(eventtime)`；本仓库 `PrinterHeaters`
只有**传感器**工厂表，`heaters: Vec<String>` 只是名字簿记，`Heater` 的 `Arc` 留在
`heater_bed`/`extruder` 各自的对象里。H1 的剩余项正是「`heaters.py` 剩余」，H2-3 需要的
只是最小面：`add_heater(name, Arc<Heater>)` + `lookup_heater(name)` + `Heater::get_temp`。

### 3.3 `tachometer_pin` → `pulse_counter`（F7）

`FanTachometer` 用 `pulse_counter.FrequencyCounter`，需要固件 `pulse_counter` 资源（F7 未动
工）。用到它的只有 3 个配置（`generic-prusa-buddy` 等），且它们都另有缺口，**不挡任何
「只差 fan」的运行**。

### 3.4 模板（`TEMPLATE=`）

`fan_generic`/`output_pin`/`servo` 的 `TEMPLATE` 走 display 模板（`display` 段本身是 53 次
缺口的 H8/H7 范畴）。`output_pin.rs` 已有「模板不在这一层」的先例；`SET_FAN_SPEED` 同样
只认 `SPEED`，`TEMPLATE` 明确报错而不是静默忽略。

## 4. 拆分建议

| 步骤 | 内容 | 转绿贡献 |
|---|---|---|
| **H2-1** | `fan.py`：`[fan]` + `Fan` 核心 + `M106`/`M107` + `get_status`（含 `gcode:request_restart`、`enable_pin`、kick start、`off_below`） | **52 次运行 1→0 缺口**，`fan` 从 197 归零 |
| **H2-2** | `fan_generic.py`：`SET_FAN_SPEED FAN=<name>`（复用 `Fan`；`TEMPLATE` 报错） | 3 次引用 |
| **H2-3** | `heater_fan.py` + `heaters::{add_heater,lookup_heater}` + `Heater::get_temp`；`klippy:ready` 起每秒 timer | 81 次引用 |
| **H2-4** | `controller_fan.py`（`stepper_enable` 查询已有） | 18 次引用 |
| **H2-5** | pin 芯片类：`multi_pin`（纯 host）、`duplicate_pin_override`（`allow_multi_use_pin`）、`pwm_cycle_time`、`static_pwm_clock` | 5 次引用 |
| **H2-6** | `servo.py`（`SET_SERVO`，20ms 周期）+ `pwm_tool.py`（固件 `queued_pwm`，F9 联动） | 4 次引用 |
| **H2-7** | LED/驱动家族：`led`/`neopixel`/`dotstar`（F9 `neopixel.c`）+ SPI/I2C digipot/DAC（`i2c_device.rs`/`spi_device.rs` 之上，约 12 个 section） | 约 30 次引用 |

前四步（H2-1…H2-4）覆盖 299/344 的缺口引用，且都是 `Fan` 核心 + 一个薄皮；后面三步按
固件资源依赖排。

## 5. 拍板点

1. **kick_start_time 怎么落地**（H2-1 就要）：
   - **A. `Reactor::call_later` 一次性定时器**：先满速，`+kick_start_time` 后把目标值落到
     PWM；靠 `Mutex` 状态 + 请求序号避免与新的 `M106` 抢。
   - B. 等 print-time 请求队列（上游 `GCodeRequestQueue`；C1d 已收官，队列仍未移植，与上游完全同形，但 H2-1 会被阻塞）。
   - **建议 A**：真硬件上风扇起转需要满速 kick，immediate 路径上用 reactor 定时器是当下
     唯一诚实的做法；C1d 后与 `GCodeRequestQueue` 统一。
2. **`tachometer_pin`**：**A. 明确报错**（写明依赖 F7 `pulse_counter`）vs B. 读了但
   `rpm: None`（静默不工作）。**建议 A**：上游配它是真的在测转速，静默降级会骗到人。
3. **排队调度**：**A. 先走 immediate**（`output_pin`/`heater` 已有先例）vs B. 先做
   `GCodeRequestQueue`（需要 C1d 三件套）。**建议 A**。
4. **H2-3 是否顺手补 heater 注册表**：建议是——那是 `heater_fan`/`controller_fan` 的直接
   前置，且正是 H1 剩余项里「`lookup_heater`」那一行，不额外扩张面。
